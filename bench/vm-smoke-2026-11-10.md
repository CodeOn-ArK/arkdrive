# VM smoke — x86 Debian 13 under QEMU/KVM on ArK2 (Raj, Nov 10, 2026)

ArK's Phase 5 rollout order: VM first (x86), then Pi 4 + SD card, then Pi 5.
This run proves the wm stack boots and operates in a clean x86 VM, which also
serves as the first clean-environment install check for the stack.

## Setup

- Host: ArK2, /dev/kvm present. `qemu-system-x86_64` (apt qemu-system-x86,
  qemu-utils, genisoimage).
- Guest image: Debian 13 cloud
  `debian-13-genericcloud-amd64.qcow2` (cloud.debian.org trixie latest,
  341 MB), resized +10G; cloud-init growpart expanded root to 13G.
- cloud-init seed ISO (cidata): user `ark`, passwordless sudo, SSH key only
  (keypair generated on the host at ~/vm-arkdrive/vm_key).
- QEMU: `-enable-kvm -machine q35 -cpu host -m 4096 -smp 2`, virtio disk +
  net, user networking with hostfwd tcp::2222-:22, headless, serial to file.
  Guest files on the host: ~/vm-arkdrive/ (run-vm.sh relaunches it).
- Guest: Debian 13 (trixie), kernel 6.12.115+deb13.1-cloud-amd64; cloud-init
  status done; SSH reachable ~10 s after launch polling began.

## Guest dependency list (what the stack actually needs)

apt: `xvfb openbox python3 python3-xlib python3-gi gir1.2-gtk-3.0 dbus
at-spi2-core x11-utils libglib2.0-bin`

- **libglib2.0-bin is easy to miss**: sessiond shells out to `gdbus` for its
  private buses. Without it, `ark-sessiond start` fails with
  `[Errno 2] No such file or directory: 'gdbus'`. ArK2's desktop install has
  it by default; a minimal cloud image does not. First smoke attempt failed
  on exactly this; after installing it, everything passed.

## Smoke result: PASS

Inside the guest, with the wm/ tree copied from the repo:

- `ark-sessiond start --profile xvfb` → session s1 ready.
- `ark-worker start --session s1`; driver attached (lease issued, rev 3).
- `fx_log --tag VMSMOKE` launched through sessiond run; the worker's full
  settled `window.observe` (state + pixels) reported windows
  `['Openbox', 'VMSMOKE']` and issued 1 frame; rev advanced to 15.
- Worker and session stopped cleanly afterwards.

Not covered here (by design): xorg profile inside the VM (no GPU/evdev
passthrough), performance numbers, persistence across guest reboot.
