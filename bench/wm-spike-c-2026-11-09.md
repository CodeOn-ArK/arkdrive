# WM Spike C — Blender GPU path inside an agent session

- Plan: ArkDrive Agentic WM, Phase 0 probe (3) — Blender renderer identification and GPU-path measurement.
- Date: Nov 9, 2026 (evening PT). Host: ArK2 (arktx), RTX 3060 12 GiB, NVIDIA driver 595.99.02.
- Harness: `~/wm-spike-c/` on ArK2 (`spike-c.sh`, `bench.py`, `run-official.sh`, all bench/smi/glx/egl logs). Sessions followed the Spike A pattern (own HOME/XDG_RUNTIME_DIR, env-marker cleanup). The real desktop session (:0) and Chromium were never touched; no display manager or driver changes.
- Fixed render spec, identical on every path: factory default scene, 640×360 @100%, Cycles 128 samples with denoising off, or Eevee 64 TAA samples; 1 warmup + 3 timed reps (5 for the headless-Eevee confirmation run), timed in-process.
- Blender under test: distro build 5.0.1 (`/usr/bin/blender`) plus, as a follow-up, the official 5.0.1 linux-x64 tarball build (kept in `~/wm-spike-c/blender-5.0.1-linux-x64/`).
- Prerequisites installed via apt during the spike: `mesa-utils` (glxinfo/eglinfo), `xserver-xorg-video-dummy`. Neither is a GPU-driver change.

## Verdict

**GPU path QUALIFIED via headless EGL (Eevee): PASS against the spike's pass bar.** Blender renders on the RTX 3060 with no X display at all — renderer string names NVIDIA, nvidia-smi shows the blender process on the GPU, and the identical render runs **8.5× faster** than the Xvfb software baseline.

**Cycles GPU: device-qualified with the official build, render BLOCKED at test time by VRAM contention** (see below). With the distro build, Cycles GPU is blocked outright by packaging.

The session's X server is not where GPU acceleration comes from: Xvfb and Xorg-dummy both hand Blender Mesa llvmpipe. GPU arrives through EGL surfaceless contexts (GL/Eevee) and CUDA (Cycles), which are independent of the display backend.

### Path 1 — Xvfb (the baseline to beat)

- glxinfo: vendor Mesa, renderer llvmpipe. Eevee median 4.792 s (reps 4.792/4.717/5.196). Cycles CPU median 0.472 s.
- Exactly the plan's risk entry, confirmed: functional UI/rendering, software performance.

### Path 2 — Xorg-dummy

- First start attempt FAILED: without `AutoAddGPU=false`, Xorg auto-added the real GPUs via modesetting (`modeset(G0/G1): Failed to create pixmap` → `failed to create screen resources`) and died. With `AutoAddGPU=false` added (config `xorg-dummy2.conf` on the box), the dummy server starts and stops cleanly.
- Once up, GL is the same llvmpipe as Xvfb and Eevee is the same speed (4.824 s median). Dummy buys input-routing properties (Spike B's question), not graphics.
- Log side-note: the dummy server's udev scan noticed a pre-existing virtual input device (`ArkDriveB S2 Pointer`, `/dev/input/mouse4`, from earlier ArkDrive work); `AutoAddDevices=false` kept it out of the session. Left untouched.

### Path 3 — Headless EGL (the GPU path that passes)

- `eglinfo` with no DISPLAY reports, on both the GBM and Surfaceless platforms: EGL vendor `NVIDIA`, OpenGL core renderer **`NVIDIA GeForce RTX 3060/PCIe/SSE2`**, version `4.6.0 NVIDIA 595.99.02`. A display-less process can open a full NVIDIA GL context through the registered NVIDIA EGL vendor (`/usr/share/glvnd/egl_vendor.d/10_nvidia.json`).
- Blender headless Eevee, identical spec: median **0.565 s** (5 reps: 0.527–0.590) vs 4.792 s on llvmpipe in Xvfb → **8.5× speedup**.
- nvidia-smi during the render run: `blender` process present with 37–38 MiB GPU memory; GPU utilization peaked at **98%**. (Blender's own `gpu.platform` calls raise "GPU functions for drawing are not available in background mode" in 5.0.1, so the renderer-string evidence comes from eglinfo in the identical no-DISPLAY environment, corroborated by the nvidia-smi process/utilization record and the 8.5× delta over the same binary's llvmpipe time.)
- Footprint matters: this path needed only ~38 MiB of VRAM, so it works even while the card is nearly full (below).

## Cycles GPU — two separate blocks, neither is the session architecture

1. **Distro Blender build (packaging block).** `compute_device_type` accepts only `('NONE', 'CUDA', 'HIP')` — OptiX is absent — and even with CUDA selected, device enumeration returns only the CPU (`12th Gen Intel Core i5-12600K`). No compiled CUDA kernels ship in the package (find shows only kernel *sources*). Result: Cycles silently renders on CPU at CPU speed (0.493 s) while nominally set to GPU. System CUDA itself is healthy: a direct libcuda probe returns `cuInit: 0`, device count 1.
2. **VRAM contention (capacity block).** The official Blender build enumerates the RTX 3060 as both CUDA and OptiX devices and enables them (`use=True`), but every render attempt fails at context creation: `Failed to retain CUDA context (Out of memory)`. At test time the two resident `llama-server` processes (the local-model servers) held 10,632 + 1,156 = 11,825 MiB of the 12,288 MiB card, leaving **87 MiB free** — below a CUDA context's needs. This held headless and inside the Xvfb session identically, confirming display independence.
   - Classification: **device-qualified (official build), render blocked by current VRAM occupancy.** Unblock condition: roughly ≥1 GiB free VRAM (context + this scene class); no re-test was possible without stopping ArK's running model servers, which was out of scope and not attempted.
   - OptiX is available only in the official build; it hit the same VRAM wall before rendering.

## Untried candidates, with reasons

- **VirtualGL**: not packaged for this distro (no apt candidate); it also renders through the live :0 X server, which this spike's safety rules exclude. The EGL result makes it unnecessary for the Eevee/viewport case.
- **Second Xorg server with the NVIDIA driver on a virtual display**: the GPU is already bound to the running :0 server; standing up a second NVIDIA X server on the same GPU would need display-manager/driver-level changes — excluded by the spike's safety rules (and unnecessary: EGL covers GL, CUDA covers compute).
- **Xpra/Xdummy as a GPU path**: Xdummy is a presentation/display backend; its GL would still be llvmpipe-class without an EGL/CUDA side channel. Belongs to Spike B / Phase 1 presentation work, not this spike.

## Takeaways for the plan

1. **Treat the GPU context as a separate session resource.** The broker should hand a session an EGL surfaceless context (and/or CUDA device access) alongside its display server; neither Xvfb nor Xorg-dummy will ever provide GPU GL by themselves.
2. **VRAM is an admission-control problem.** Eevee-class GL work fits in ~38 MiB and coexists with a resident local model; Cycles CUDA needs a real VRAM budget. Session admission should check free VRAM against the workload class before promising a GPU Cycles render.
3. **Ship a Blender build with CUDA kernels** (official build or equivalent) in the Phase 5 image; the distro package cannot enumerate CUDA devices and has no OptiX. Re-run this spike's Cycles leg on the shipped kernel/driver tuple, per the plan's Phase 5 changes to Phase 0, once VRAM headroom exists.
