## Implementation

1. **Route table:** `wm/worker_routes.py` owns the ordered operation ladder,
   route states, consecutive miss counters and atomic shared persistence.
   `Engine.route_context` derives the six-part key from the canonical profile
   hash, application build, observed toolkit, target/tree surface role, intent
   kind and keyboard/pointer class. Metadata collection hashes the executable
   behind a session-marked window PID, cached by executable stat identity.
   Unmeasured builds use the window class plus generation, deliberately avoiding
   reuse across unknown builds. Toolkit is collected in the provider snapshot;
   absent toolkit information is explicitly `unknown`. With no tree target,
   surface role falls back to the probe root role, then the window type.

2. **Ladder:** xvfb uses XTEST; xorg uses evdev then XTEST. Text adds paste then
   editable-node AT-SPI set-text; ref clicks with actions add AT-SPI invoke.
   Scroll/move/drag/key have physical routes only. Invoke remains AT-SPI only;
   WM intents retain WM routing. Auto text uses keys first only when every
   character maps on the session keymap and length is at most 200. Explicit
   `via:keys` excludes paste/AT-SPI; `via:paste` starts at paste. Explicit route
   requests restrict eligible routes. All routes remain inside the session.
   Replacement on keys/paste selects all before typing/pasting; set-text replaces
   by definition. The original expectation is retained on every rung, including
   insertion expectations when the fallback operation itself replaces text.

   Within-step advancement requires aggregate proof that nothing was dispatched.
   Unknown delivery, partial delivery and acknowledged absence of effect never
   trigger a harder route. Existing idempotent absolute-move/focus retry behavior
   is retained. There are at most three route attempts per step. Previously,
   `attempts[]` counted individual motion/key/chunk writes; it now counts rungs,
   with exact original write/ack records retained in `input_groups` when grouped.
   Cleanup writes are retained under `cleanup.attempts`, outside the rung limit.
   `route_change: {from,to,reason}` is recorded on the affected step receipt;
   learned starting-rung changes use reason `learned_route`.

3. **Paste:** `wm/worker_paste.py` lazily creates one **unmapped** owner window
   on the worker's existing session-only `ev` X connection. It reuses that window
   for later pastes and never restores the old clipboard. Creation and ownership
   each check authority immediately before the write. Ownership is confirmed by
   asynchronous GetSelectionOwner, without a blocking round trip or subprocess.
   X ownership errors update paste health with the actual failure. The owner
   event loop serves TARGETS, UTF8_STRING and STRING; STRING uses Latin-1 with
   replacement for characters it cannot represent. Serving data and notifying
   the requestor also check authority. The content/window survive verification
   and remain owned until another client takes ownership, the next paste replaces
   the content, or the worker connection closes. Data is served while the saved
   action authority remains valid. No host clipboard connection exists.

   Ctrl+V uses the current healthy session physical channel (XTEST on xvfb,
   evdev or XTEST on xorg); replacement first sends the profile's select-all.
   The attempt records `input_route`, `clipboard_overwritten:true` and
   `selection_requested`. Target-client requests are identified by the X client
   resource base, including unmapped transfer windows. Selection evidence is
   copied into both step and attempt and frozen when verification finishes, so
   late requests cannot alter a durable receipt. Failure to request the selection
   remains an ordinary `not_observed` outcome. Before lazy creation, system.info
   reports paste unavailable/not_created; afterward it reports ok, or the real
   ownership failure.

4. **AT-SPI:** the existing provider child accepts `set_text` with node key,
   role/name guards, text and control generation/epoch/deadline. The child
   rechecks live enabled/sensitive/editable state immediately before guarded
   EditableText.setTextContents. Window-only text can use the unique observed
   focused editable node; its focused state is checked again in the child.
   Ref-click fallback uses exactly the existing invoke request/default action.
   No pyatspi import or direct semantic call was added to the worker.
   Already-degraded/non-sent requests are not_dispatched; sent timeouts remain
   unknown. Both routes use the existing expectation/verification path.

5. **Rejection inference:** two consecutive complete raw-ack XTEST steps with
   target focus at dispatch/deadline, not_observed effect and unchanged target
   family flip only that table entry. Family checks include metadata revision
   stamps (so changed-then-restored data still counts as reaction), geometry,
   tree facets, pixel tiles when present, membership and removed windows.
   Any independently falsified condition breaks the streak; verified steps reset
   it. The second receipt has reason `synthetic_input_rejected_suspect` in its
   route_change, with the next eligible rung or null. Later exhausted xvfb steps
   fail undispatched with backend_unsupported/xtest_rejected and
   `escalate:relaunch_on_xorg`; xorg with evdev down plus rejected XTEST escalates
   to restart_session. Unknown/input_unacknowledged marks its entry route suspect;
   the existing independent 1 px out/back raw-ack probe tests that physical
   channel. Failure marks it down for the generation; success leaves it suspect
   until a subsequent verified step. Probe evidence is retained on failure too.

6. **Fixture:** `wm/fixtures/fx_log --reject-xtest` already intercepted and dropped
   XTEST-source events. Those dropped events now have kind `rejected_input`,
   preserving source-device and event fields. Other sources, semantic text
   writes, and default behavior retain their prior dispatch/logging behavior.

## Route-table format and recovery

`STATE/route-table.json` is under the sessiond state root, shared by sessions,
not inside a session directory. Example (hashes abbreviated):

```json
{
  "version": 1,
  "entries": {
    "[\"profile-sha256\",\"exe-sha256\",\"gtk\",\"entry\",\"text\",\"keyboard\"]": {
      "identity": {
        "profile_hash": "profile-sha256",
        "app_build": "exe-sha256",
        "toolkit": "gtk",
        "surface_role": "entry",
        "operation": "text",
        "input_class": "keyboard"
      },
      "routes": ["xtest", "paste", "atspi"],
      "states": {
        "xtest": {"state": "rejected", "misses": 0, "generation": "generation-id"},
        "paste": {"state": "ok", "misses": 0},
        "atspi": {"state": "ok", "misses": 0}
      }
    }
  }
}
```

Keys encode the ordered six-element tuple as a compact JSON array string.
States are ok/suspect/rejected/down. Entries start at ok in memory. All flips
out of ok and recoveries are persisted with file fsync, atomic replace and
parent-directory fsync. A sibling `route-table.lock` serializes writers;
per-route merging preserves independent flips even for the same entry.
Miss counters are local to a worker and serialized as zero: flips, rather than
unfinished inference, are shared. Missing, corrupt or malformed files load as a
fresh table. A new worker loads rejected entries before dispatch. A new
generation's healthy channel proof permits persisted down routes to recover;
suspect needs a subsequent verified step. Rejected hints remain sticky for that
profile/build/key. Route eligibility is recomputed from each current target.

The profile policy hook is:

```json
{"applications":{"<executable-build-sha256>":{"synthetic_input":"rejected"}}}
```

A WM_CLASS application key is also accepted for fixtures/policy classification.
This starts that entry's XTEST state rejected without probing. The worker reads
canonical profile JSON from session-record `profile_data`, otherwise optional
`SD/profile.json`, otherwise its existing development profile. The resulting
profile data participates in the profile hash, so policy changes invalidate old
keys. No executable launcher, adapter or loop changes were made here.

## Contract interactions and limits

- **Existing F2 fence versus §4.7's probe:** the existing two-unknown-delivery
  fence, a closed control gate, an expired batch or an existing fence can suppress
  a diagnostic probe. W8 retains those fences as required by the explicit scope
  constraint; it never writes probe input after authority closes. The entry is
  still marked suspect. For an incomplete raw acknowledgement the admitted probe
  uses the same physical channel. The older independent F2 liveness check after
  a helper has already failed can use surviving XTEST; it does not retry the
  intent. This is the retained F2 interaction with an unconditional reading of
  Fable §4.7, not an application fallback.
- **Three-attempt bound:** an xorg text ladder has four possible rungs. If the
  first three all fail before dispatch, AT-SPI is deferred to a later driver step;
  the same step never takes a fourth attempt. This follows §4.6's explicit limit.
- **Unknown application builds:** no cross-generation learning is claimed until
  the worker can measure the session application's executable. This is a
  conservative identity fallback, not a claim that WM_CLASS is a build hash.
- No CDP, OCR, frame, adapter/loop or verification-strength changes. Live timing,
  first-route success rate and desktop acceptance remain unmeasured here.

## Fix round 1

2026-11-11, headless only. Raj's E5 report identified the missing boundary:
publication of a completed semantic page does not establish that the page is
post-dispatch evidence. There was no dispatch-relative tree freshness check in
`Engine.verify()`. One diagnosis detail needs qualification for this checkout:
`Provider.evaluate(node_state)` returned only a boolean/unknown; the existing
`contradicted` exit was in the separate focus/modal/window transition check.
Thus a false node-state reading alone did not reproduce that exit in this
headless harness. The exact transition behind Raj's live receipt is not
established here; this is not a claim of a live reproduction or a passed E5.

`Engine.verification_verdict()` now routes submitted tree predicates through
`Provider.effect_verdict()`. The deciding target-window facet must satisfy
`StateCache.facets['tree[' + window + ']'] > step.rev.dispatched`.
Both equality and an older facet mean **not yet**, for positive as well as
negative readings. Verification keeps sampling and a healthy provider with no
newer deciding tree ends `not_observed`, reason `timeout`. Unrelated tree facets,
pointer/geometry changes, global revision advancement and X-only refreshes
cannot make the target tree fresh. Existing provider-down/breaker/unavailable
recovery uncertainty retains `unknown/provider_degraded`.

Bookkeeping reused: the existing **StateCache per-facet revision clock** and
the step's existing **rev.dispatched** boundary, already used by dependency and
selector staleness guards. No second dispatch timestamp or parallel freshness
counter was added. The W4 **publication-versus-freshness split** remains intact:
completed pages stay publishable, while the provider's ordinary dirty-snapshot,
per-window invalidation tokens, health and inventory checks still govern their
semantic usability. An identical snapshot that does not advance the facet is
not new deciding evidence under this rule. Admission, preconditions, independent
wait steps and reconciliation continue using their existing read semantics.
