# laneq — ArK2 shared desktop queue, 2026-11-10

## Design and delivered files

One shared lane covers the legacy `:0` desktop driven through `~/bin/cua`.
A work owns the lane for its entire process-group lifetime, across calls and
LLM pauses. Queue order is priority descending, then creation time ascending.
Group-leader PID existence (`os.kill(pid, 0)`) is the only liveness criterion;
there is no heartbeat timeout. Dead holders and dead pending tickets are
cleaned during acquisition.

All state transitions use an exclusive `flock` on `claim.lock`; claimants
recheck slot availability and queue-head identity inside that lock. JSON
updates use temporary files plus `os.replace`. Audit JSONL includes all six
specified event types with timestamp, ticket, owner and PGID. Status excludes
the holder from the pending queue; its ticket remains on disk until release.

New files:

- `tools/laneq/laneq.py`: stdlib queue CLI (`acquire`, `release`, `status`,
  `run`, `clear --force`).
- `tools/laneq/cua_shim.py`: queues writes; directly execs real cua for
  `shot`, `win list`, `tab list`, `clip get`, or when `LANEQ_OFF` is set.
- `tools/laneq/install.py`: backs up and verifies the original launcher,
  installs both executables, refuses conflicting backups, supports isolated
  test directories and rerunning an existing installation.
- `tools/laneq/tests/test_laneq.py`: headless integration tests.
- `tools/laneq/README.md`: operation, environment, recovery, process-group
  identity, read/write split, xdotool wrapping and scope.
- This evidence note.

`laneq run` launches the command in its existing process group, releases on
exit/SIGTERM/SIGINT, and preserves child exit status. It stops its direct
child before signal-triggered release, escalating to SIGKILL after 3 seconds
if necessary. Independent scripted works must start in separate groups
(e.g. `setsid laneq run -- ...`). Non-cua writers such as xdotool must wrap
the entire work in `laneq run`.

Portal lanes (`:11`–`:13`), qwen-executor sources, pipeline scripts and `wm/`
were not modified. No files were staged or committed. Existing unrelated
workspace changes were left alone.

## Headless evidence: PASS

Command:

```sh
python3 -m unittest discover -s tools/laneq/tests -v
```

Final result: **24 tests passed, 0 failures/errors, 22.504 seconds**.
An earlier 23-test run also passed before signal cleanup was strengthened.
Every test has isolated `LANEQ_HOME` and bin directories. The installer runs
against a generated stub; shim tests set `LANEQ_CUA_REAL` to the copied stub.
Group leaders are `sleep` processes or Python wrappers started with setsid.
No test invokes real cua, X11, or desktop input.

Coverage:

- FIFO with two pending works; both block behind a live holder, then claim
  in order across explicit releases.
- Dead holder auto-release; dead pending ticket cleanup; a live leader
  retains ownership even when `last_seen` is artificially set to zero.
- Fast-path refresh, one ticket per PGID across timeout retries, idempotent
  release and pending-ticket cancellation.
- Priority jumping the queue while leaving the current holder in place.
- `run` serialization, same-group children, exit-code propagation,
  SIGTERM/SIGINT cleanup, cancellation while queued, and cleanup of a direct
  child ignoring SIGTERM.
- Timeout exit 3, JSON fields, 1-based pending position, audit fields,
  status shape, force-clear cleanup and audit retention.
- Explicit/environment/proc-derived owner selection.
- Shim writes wait behind a different group; all four read-only command
  forms pass immediately behind a live holder; `LANEQ_OFF` bypasses writes
  even with an empty value. Unknown/incomplete arguments queue as writes.
- Shim timeout emits exactly one JSON line and never calls the stub;
  successful writes emit only stub output. Unicode/newline arguments,
  stdin and real exit codes pass through.
- Installer verifies both stub backups byte-for-byte and by SHA-256,
  supports rerunning, and refuses conflicting backups without replacing cua.

Two overlapping 2-second sleeps under `run` took **5.105 seconds** in the
final run (required minimum: approximately 4 seconds). Monotonic markers:

```text
one start 1862801.284364841 95
one end   1862803.284539119
two start 1862804.334325755 97
two end   1862806.334501788
```

Markers do not interleave. The child's group IDs match its respective
`laneq run` PID. Polling can add up to 1.5 seconds between works.

## Host installation: NOT RUN

The session's managed filesystem policy permits writes only in
`/home/ark/arkdrive` and `/tmp`, with permission escalation disabled.
`/home/ark/bin` is outside those writable roots. The actual launcher has not
been moved or replaced, and host `cua.real`/`cua.bak-laneq` have not been
created. Coordination is therefore **not active on the host yet**.

The original `~/bin/cua` SHA-256 was measured before and after implementation
and is unchanged:

```text
38d489232975578a583582c89d74e76d26b111aeab04b5bdcc7dd54c8a744f90
```

Backup checksum proof currently applies to the isolated stub installations
only. Run the prepared installer from an environment with write access to
`~/bin`; it verifies both real backup hashes before replacing the launcher:

```sh
python3 ~/arkdrive/tools/laneq/install.py
sha256sum ~/bin/cua.real ~/bin/cua.bak-laneq
```

Both host backup hashes must equal the original hash above (assuming the
launcher has not changed since this build). The installer prints the three
measured hashes as JSON; preserve that output with live verification.
