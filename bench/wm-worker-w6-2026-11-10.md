## STOP finding and remaining authority gap

Static review found a teardown/grab-loss race. `ark-sessiond.teardown` sends
FIFO `quit` to mkdevs and waits **3 seconds**, then signals the recorded
processes, beginning with Xorg. `EventSocket.close` waits for its serving
thread to finish the current request. A permitted 64-frame request at
`gap_us:50000` has **63 × 50 ms = 3.15 seconds** of inter-frame pacing alone.
The helper can therefore outlive that wait with writes still pending while
Xorg releases its grabs. Session input could then reach the kernel's other
consumers. The FIFO path is intentionally unchanged in this scoped build.
**This is a STOP for live evdev admission, not a timing optimization to work
around.** No teardown reordering, weakened grab, host input fallback or
larger timeout was introduced to hide it. Raj needs to resolve the lifecycle
contract before enabling the live channel. The worker's own graceful stop
closes the existing control gate before draining an outstanding reply; that
does not resolve independent sessiond teardown or abrupt Xorg/grab loss.

There is also a pre-existing integration gap against reconciled R9/§4:
the worker/sessiond do not provide the adopted closed-gate broker bind
registration, PID/starttime/device-identity ceremony or a live host-sentinel
registration. W6's scoped Fable stream protocol authenticates the owner UID,
checks the control generation/epoch, pins the first admitted generation for
the device lifetime, and deduplicates chunks; **these are not a claim that
the full R9 ceremony exists**. It must not be treated as production input
admission without those requirements being resolved. No sentinel or broker
protocol was invented to work around this gap. No grab-routing contradiction
was found by static reading; actual routing under the grab remains C4.

## Protocol a verifier needs

`SD/input.sock` is AF_UNIX/SOCK_STREAM, bound under umask 0177, owned by the
session UID with mode 0600. Only one accepted peer is served at once; a
second peer is closed. SO_PEERCRED UID must equal launch-time --owner-uid;
a mismatch is closed before parsing/writing. No descriptor is returned.
Each request and reply is a 4-byte unsigned big-endian body length followed
by UTF-8 JSON. A body must be 1..65536 bytes. Fragmentation and multiple
requests on a persistent stream are supported. Invalid framing disconnects;
invalid JSON/schema yields rejected without input.

Example event request (numbers are Linux event codes):

```json
{"seq":1,"generation":"0123456789abcdef0123456789abcdef","dev":"kbd","frames":[[[1,42,1]],[[1,42,0]]],"gap_us":2000}
```

Event requests have exactly seq, generation, dev, frames and gap_us. seq is
a nonnegative integer; generation is the worker's 32 lower-case hex digits.
Frames are nonempty, at most 64; each has 1..4 integer triples. Booleans are
not integers for validation. kbd accepts EV_KEY codes 1..248 except 99,
values 0/1. ptr accepts EV_KEY 0x110..0x112 values 0/1 and EV_REL 0/1/6/8
values -40..40. gap_us is integer 0..50000. The entire request is validated
before any write, including valid prefixes followed by invalid events.
The helper adds EV_SYN/SYN_REPORT after each frame and sleeps only between
frames, never after the last. Before every frame it reopens/double-reads the
64-byte control file and requires valid magic/version, the request's
generation, AGENT, nonzero unchanged epoch and zero permit field. Missing,
short, torn, wrong-generation and closed pages stop before that frame.

Replies contain seq, ok, frames_written and error
(null/gate_closed/rejected/io_error). frames_written counts complete frames
including successful SYN_REPORT writes. A conservative may_have_written
extension distinguishes a write entered before an incomplete first frame
from a whole-request refusal: the worker never declares non-dispatch for an
I/O error after a possible event prefix. It is not an invented exact count
for a lost reply. Completed-frame counts remain exact.

Ops are `{"seq":N,"op":"release_all"}` and
`{"seq":N,"op":"grab_check"}`. release_all writes key-ups only for the
helper's own currently held keyboard/button set, with SYN_REPORT per device;
it is allowed through a closed gate. grab_check adds kbd/ptr busy/free to the
usual reply. It opens only its assigned nodes, calls EVIOCGRAB, reports busy
only for EBUSY, and immediately releases a successful grab. Other probe
errors report io_error, never a fabricated busy result.

Same seq plus same canonical payload returns the stored reply without
writing again. Changed payload is rejected. The last 4096 replies are kept;
older sequences below the high-water mark are rejected even after eviction,
so eviction cannot cause a repeated write. Deduplication and generation pins
survive reconnects, not helper/device teardown. Sequences are global to the
helper lifetime: a verifier's direct negative request must use a fresh seq
and must not collide with a running worker. Prefer a dedicated scratch
session, or send the negative request after the delivery run. A changed
worker generation requires new devices for evdev; the surviving session can
still use XTEST under W1 restart semantics.

## Worker behavior and evidence

The existing XTEST session keysyms/characters choose X keycodes. At xorg
startup libxkbcommon-x11 compiles the assigned keyboard slave's own XKB map
on a temporary connection explicitly addressed to the verified session
display. Physical key names resolve through worker_keymap.py to Linux codes;
no fixed offset is subtracted from session keycodes. The temporary connection
is closed at startup. Missing libraries/map/slaves fail evdev closed; there
is no action-path subprocess or host keyboard lookup. The API reference is
[libxkbcommon X11 support](https://xkbcommon.org/doc/current/group__x11.html).
Keyboard mapping or hierarchy changes retire the compiled evdev channel for
this generation rather than trusting stale identities.

Key chords/text use one EV_KEY per frame, default gap_us 2000. Pointer frames
use gap_us 0. Motion is derived from a fresh session QueryPointer and split
into relative X/Y components of at most 40; left/middle/right map to
0x110/0x112/0x111. Scroll uses REL_WHEEL/REL_HWHEEL and expects the server's
corresponding raw button press/release pairs. Requests are split at device
boundaries and 64 frames. Drags retain the existing engine timing/targeting.
A chord containing Sys_Req or Print is invalid_request on evdev before even
grab-check traffic. Explicit XTEST still sends those keysyms unchanged.

Both assigned slaves must report busy at startup and again before the first
evdev input of each batch. Otherwise evdev goes down/no_exclusive_grab and
XTEST is selected when available. A healthy xorg channel is primary for
key/text/click/scroll/move/drag. Receipts record the actual route. No route
table, learning, rejection inference, paste or AT-SPI fallback rung was added.

Ack uses the existing ordered matcher over the shared XI2 raw stream. Both
device and source IDs must equal the assigned keyboard/pointer slave; master
copies and other sources do not count. Full expected counts within 150 ms
plus request pacing are accepted; short counts are unknown with
input_unacknowledged. Late raw events can reconcile without resending input.
The existing gated pointer probe handles ack failure; a failed probe marks
the affected channel down. Acknowledgement never proves application effect.

Transport gets at most one reconnect for the generation. Recovery resends
only the identical seq/payload so the helper cache can recover a lost reply.
Failure before the complete request was submitted is not_dispatched; an
unrecoverable lost/invalid reply after submission is unknown (reconciled R7).
A refusal at zero frames is not_dispatched and retires evdev after the single
reconnect opportunity. Partial completed frames are accepted/channel_down,
with exact per-attempt frames_written/written/written_prefix.frames and
step written totals; release_all is issued, evdev goes down and the step is
never reissued. No subsequent step is dispatched. Subsequent eligible acts
can use XTEST; the partially written step is never replayed through it.

Held evdev input is released through the helper; QueryKeymap/QueryPointer
independently confirm release on the session server. Failure to confirm
fences F1. Graceful stop closes the existing xorg control gate, drains an
in-flight reply before sharing the stream with release_all, then releases.
This is worker-stop behavior, not a resolution of the STOP finding above.

Startup tests reuse the override-redirect surface. With no clients, each
channel sends 50 Shift_L down/up pairs and 100 alternating 1-pixel moves:
200 events per route, exactly 50 test-window key presses, final pointer at
origin and raw counts from the assigned source. A late attach sends only
100 pointer moves per route and leaves keyboard untested. Its first verified
keyboard step marks that route tested. Evdev failure plus a passing XTEST
test allows startup; both tests failing prevents startup. An owner-closed
control page still defers input tests as in W2.

For instantiated xorg channels system.info reports:

```json
{"evdev":{"state":"up","grab":true,"keyboard":"tested","last_error":null}}
```

state is up/down/untested; keyboard is tested/untested. grab records the last
probe (true requires both busy), not a claim of a continuously proven grab.
Failures are retained in last_error and down is latched for the generation.

### Evdev establishment and Xorg settlement

The A2 evidence establishes the missing distinction in fix round 2:
MappingNotify and XI2 HierarchyChanged are also normal events while Xorg
finishes attaching the session's own keyboard/pointer slaves. The old event
handler retired evdev before a usable map, slave pair and startup grab check
existed. Containing the resulting transport close let XTEST start, but made
evdev admission impossible on these starts.

`EvdevTransport.established` now records a separate bootstrap boundary. It
becomes true only after fresh slave discovery, successful compilation of the
current assigned keyboard's keymap, a successful busy/busy `grab_check`, and
a final round trip on the X event connection with no intervening mapping or
hierarchy revision. Establishment precedes the existing delivery self-test;
it does not claim successful delivery or promote channel health to up.

Before establishment, either notification increments a dirty revision and
restarts a **50 ms quiet interval**, including across separate event-ingestion
batches. Bootstrap initially waits the same interval. After quiet it sends
a new XIQueryDevice to the verified session connection, clears the previous
slave snapshot, discovers the enabled assigned slaves, and compiles that
keyboard's current map. It never bootstraps from XTEST's cached device list.
A discovery result superseded by an event is discarded before compilation.
A round trip after compilation orders already-generated notifications before
accepting the result or reporting a discovery/compile failure. Another round
trip follows `grab_check`; changes during that probe or either barrier
restart the quiet/discovery/compile/probe cycle. A free probe concurrent with
settlement is retried after settlement; a stable free probe still fails
closed. No evdev input is sent before establishment.

Discovery replies and barriers have 250 ms waits; continuing settlement is
bounded by a 2-second bootstrap budget and reports
`session_settlement_timeout`. Stable missing/error/timeout discovery reports
`assigned_slaves_unavailable`, compilation failure reports
`session_keymap_unavailable`, and a stable failed grab reports
`no_exclusive_grab` (transport faults retain their initiating cause). Each
failure leaves evdev down and lets the complete XTEST diagnostic run and
publish ready if XTEST passes. These are debounce and protocol-ordering
semantics: a later notification after establishment still retires evdev for

### Cache refresh and diff rule

After establishment, MappingKeyboard and MappingModifier notifications mark
evdev's map dirty without changing channel health or closing its connection.
A cooperative refresh runs even without an active action. It uses the same
50 ms quiet interval, fresh XIQueryDevice discovery, current assigned slave

probe or either barrier invalidate the candidate and restart settlement.
The existing 2-second settlement budget and 250 ms query/barrier waits remain.
The established source pair and table remain intact until the candidate is
accepted; a candidate from a superseded revision is never adopted.

The diff compares the complete compiled dictionary of X keycode to evdev code
using dictionary equality (order does not matter). Each successfully settled
post-establishment refresh increments `system.info.channels.evdev.recompiles`,
initially zero. Notifications within one unsettled burst may coalesce into
one completed refresh; bootstrap compilation and discarded candidates do not
increment it. An identical table preserves state, grab, keyboard health,
last_error and the helper connection. MappingPointer does not dirty this
keyboard cache.

A different table is adopted atomically, advances an internal map epoch and

uses the conservative rule: any added, removed or changed entry demotes the
keyboard, without trying to infer which entries future driver macros will
use. Only a verified keyboard/text step dispatched on the current epoch can
promote it again. A previously dispatched step that verifies after adoption
cannot promote the replacement table. The regression also checks actual
helper frames use the adopted code before keyboard promotion.

### Admission, self-test and retirement

semantics, observing control and step deadlines. They do not switch routes
or send frames with the stale table. Plans carry their table epoch through
helper-stream serialization. If a macro's table changes after planning, its
remaining frames fail with `provider_degraded`; any submitted prefix keeps

replayed. A partially sent packet is cancelled before its final bytes can
submit it, freeing the stream for the refresh probe without retiring evdev.

refreshes pause and resume that diagnostic without resetting its health.

## Fix round 5

### Root cause and recovery

Raj's live E2 kill correctly stopped the text macro, but also removed the only
writer that could release its device keys. The worker retained the possible
holds, `release_all` could no longer deliver key-ups, and F1 correctly prevented
all subsequent dispatch. Reconciliation could not repair device state. A fresh
helper with an empty local held set would also be insufficient: its empty
`release_all` would not release the previous process's device keys.

Sessiond now launches `mkdevs.py --supervise` for xorg sessions. Its privileged
supervisor creates the keyboard/pointer once and retains their uinput open file
descriptions. An event-serving child inherits those same descriptors; killing
that child does not destroy or replace the devices or Xorg's assigned slaves.
The supervisor polls/reaps a dead child before forking its replacement. It
neither recreates devices nor rewrites the control page during recovery.
`mkdevs_supervisor_pid` identifies the supervisor in the session record;
`devices.json.pid` publishes the current serving child's PID, including after
respawn. The record's initial `mkdevs_pid` may predate a respawn, so teardown
reads the final child PID after stopping the supervisor.

Each child atomically publishes a fresh random incarnation token in
`input.sock.instance` after its socket listens. The worker checks the existing
socket permissions and the private, owner-UID token file on connection. Every
supervised helper request carries that token. The helper rejects mismatched
tokens before touching its sequence high-water mark or cache. This also covers
the replacement-socket/stale-metadata race. The worker never sends an old ACT
request to a newly observed incarnation; an old token reaching a replacement
socket cannot execute there either. Same-incarnation reconnects retain the
existing identical-payload reply-cache dedupe behavior.

The device-lifetime generation pin lives in shared anonymous memory retained by
the supervisor. The helper sets it before any press; a replacement inherits the
same pin and re-admits only that worker generation. The replacement has a new,
empty reply cache and sequence space. The worker resets its sequence for the
new incarnation's cleanup. No ACT frames or pending requests are inherited or
replayed. Peer-UID authentication, control checks, code-99 refusal and per-frame
grab liveness remain on the existing helper path. A known zero-write refusal
restores the pre-submission hold snapshot, retaining earlier groups' holds;
a different worker generation's rejected presses cannot manufacture stuck
keys or an F1 fence.

Before submission the worker records possible X keys/buttons and their actual
Linux wire codes, including candidates in a request whose lost reply makes its
prefix uncertain. Successful frames update holds in event order. Crash cleanup
uses these captured codes, independently of later keymap refreshes, in the new
`release_held` operation. This operation is generation-pinned and can write only
key/button ups plus SYN_REPORT, including with a closed gate or lost grab.
It cannot carry motion, presses, code 99 or arbitrary frames. The worker waits
cooperatively up to two seconds for a usable helper and submits releases only.
It then runs the existing independent X QueryKeymap/QueryPointer confirmation,
with the existing 150 ms confirmation budget. Helper acknowledgement alone
never clears holds or permits later input.

A confirmed release avoids F1. Evdev deliberately stays down for this worker
generation, preserving the initiating error, so subsequent acts use XTEST after
the existing reconciliation/fresh-observation requirements. The interrupted
macro retains its original channel-down/partial-or-unknown receipt and never
continues on another channel. F2's existing independent pointer liveness probe
also uses surviving XTEST after confirmed cleanup; probing the retired evdev
channel otherwise caused a second, artificial permanent fence. An F1 fence
also blocks the startup XTEST diagnostic from dispatching input.

### Failure containment, teardown and journal

Missing devices, a dead supervisor, unavailable/invalid incarnation metadata,
an incompatible pin, exhausted recovery, failed release writes, or a query
that still reports a held key/button leave cleanup unconfirmed and latch F1.
The existing explicit new-epoch `--clear-fence` path remains in place. It cannot
clear while holds remain; confirmed cleanup can remove those holds, and the
operator clear still requires the existing journal validation and new attach.
This change adds no automatic F1-clear path.

Sessiond creates `helper.lock` as the session owner before launching the root
supervisor, preserving its ability to acquire the lock at stop. Under that same
lock, teardown closes the control gate and writes `helper.stopping`; the
supervisor checks it under the lock immediately before fork. A stopping session
cannot respawn. Teardown sends FIFO quit, waits for the supervisor/child to
exit (with the existing kill/wait fallback), reads the current child PID, and
proves both processes dead before any Xorg signal. Every Xorg signal retains
that guard. Device destruction remains in the supervisor's final teardown,
after its child has been killed/reaped. Legacy unsupervised and xvfb teardown
checks remain green.

Repeated verification/finalization cleanup calls now reuse the failed outcome
for the same action and unchanged hold set, instead of issuing/logging identical
release attempts four times. Evdev writes one `release_armed` record before the
attempt, including captured wire holds, and one durable `release` outcome with
`confirmed`, route and helper incarnation. Successful cleanup clears holds;
a genuinely new hold acquisition or separate release attempt gets its own
outcome. Release remains possible under journal failure as before.

`system.info.channels.evdev` exposes `release_pending: true` during recovery
and observation. An unconfirmed evdev release adds
`fenced: "F1:release_unconfirmed"`, while retaining the underlying transport
`last_error`. A driver can distinguish a pending release or fenced session
from ordinary evdev degradation. Confirmed recovery removes the pending field;
a successful explicit fence clear removes the fenced field.
