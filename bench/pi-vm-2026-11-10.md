# Pi VM — Raspberry Pi OS arm64 under QEMU on ArK2 (Nov 10, 2026)

ArK approved testing the Pi image in a VM (Nov 10, 2026: "You can test RPI
image in a VM"). This is the Phase 5 rollout step between the x86 generic VM
(bench/vm-smoke-2026-11-10.md, bench/vm-gui-apps-2026-11-10.md) and Pi 4 /
Pi 5 hardware. Goal: validate the ArkDrive stack on the Pi OS userspace
(arm64, Debian-family), not to emulate Pi peripherals.

## Image

- Raspberry Pi OS (desktop, arm64), 2026-10-06 release, Debian 13 (trixie)
  base: 2026-10-06-raspios-trixie-arm64.img.xz (1,364,720,984 bytes) from
  downloads.raspberrypi.com/raspios_arm64.
- SHA-256 verified against the official .sha256 before use.
- Layout: p1 512 MB FAT32 (boot), p2 5.8 GB ext4 (root); image grown to
  16 GB on the host so the first-boot resize has room.
- Kernels on the card: 6.18.50+rpt-rpi-v8 (kernel8.img + initramfs8) and
  6.18.50+rpt-rpi-2712 (kernel_2712.img + initramfs_2712). A shipped
  initramfs IS present for each kernel (uncompressed cpio).
- Pre-seeded on the boot partition before first boot: userconf.txt (user
  ark, random hashed password kept at ~/vm-pi/guest-pass.txt, mode 600)
  and the empty ssh flag file; a serial getty on ttyAMA0 was enabled in
  the rootfs for console access. QEMU aarch64 installed on ArK2
  (qemu-system-arm 10.2.1) + qemu-efi-aarch64.

## Route (a): qemu virt + the card's own kernel/initrd — BLOCKED

Config: -machine virt -cpu cortex-a72 -accel tcg,thread=multi -m 4096
-smp 4, kernel8.img + initramfs8 extracted from the boot partition,
root=PARTUUID=9586d7bf-02, disk and NIC presented as virtio, then (after
the virtio check below) as USB: qemu-xhci + usb-uas/scsi-hd for the disk
and usb-net for networking.

Result: the Pi kernel boots cleanly under virt and the initramfs starts,
then waits forever for the root device and drops to a shell:
"ALERT! PARTUUID=9586d7bf-02 does not exist."

Root cause, established from the image itself (not guessed):
- No virtio transport drivers exist for the rpt kernels: no virtio_blk /
  virtio_pci / virtio_net modules in either module tree, and
  modules.builtin has no virtio entries at all. (uinput.ko IS present as
  a module in both trees.)
- More fundamental: /boot/config-6.18.50+rpt-rpi-v8 and
  config-6.18.50+rpt-rpi-2712 both have CONFIG_PCI=y with only
  CONFIG_PCIE_BRCMSTB=y (the Pi SoC host) — "# CONFIG_PCI_HOST_GENERIC
  is not set". QEMU virt exposes every device (disk, NIC, xhci) behind
  its generic ECAM PCI host, which this kernel cannot drive. The serial
  log shows PCI initializing but no host bridge probe, no xhci, no USB
  enumeration; uas and usb-storage ARE built-in and registered, they
  just never see a bus.
- So under virt + stock Pi kernel, NO disk and NO NIC can ever appear.
  This is a property of the stock Pi kernel config, not of our stack.

## Side attempt: qemu raspi4b machine — no console, abandoned

Three boots of -machine raspi4b (BCM2711 emulation, SD = the card):
(1) SD firmware path with the stock cmdline.txt (console=serial0, a
hardware alias Linux does not resolve), (2) direct -kernel with explicit
console=ttyAMA0 + console=ttyS0, (3) SD firmware path with cmdline.txt
rewritten to console=ttyAMA0. All three: zero bytes on the serial log
after 40-100 s, no QEMU errors. Recorded as attempted; not pursued
further because route (b) is the prescribed next fallback.

## Route (b): Debian 13 arm64 on virt — NOT RUN (pending go-ahead)

Planned as the exact mirror of the x86 generic VM (netinst ISO +
preseed, AAVMF UEFI, virtio disk/net, SSH hostfwd :2223, same package
list, then the same session/worker smoke + GUI app checks, scripts
prepared). It was not started: the reference setup data pulled for it
(the existing VM's preseed file contents and the ISO listing) failed
an automated safety check on the way in, so none of it was reused, and
the run is held for the parent/user to confirm proceeding with
independently written setup files.

## What this proves / does not prove so far

- Proves: the stock Pi OS arm64 image cannot be booted on QEMU virt with
  its own kernel (no generic PCI host in the kernel config), and the
  raspi4b emulation produced no usable console on this QEMU build.
  Neither says anything bad about the ArkDrive stack — the blocker is
  below the OS, in kernel/emulation plumbing.
- Does not prove anything yet about the stack on arm64 userspace; that
  is exactly what route (b) (same Debian 13 trixie base, arm64) or real
  Pi 4 / Pi 5 hardware will establish.
