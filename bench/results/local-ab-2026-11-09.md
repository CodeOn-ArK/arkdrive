## What actually happened

- **Run A** did everything structurally right: file created, saved, `verified/`
  created, file moved, root copy absent, apps closed. But the saved file is
  184 bytes ending in `done\n\n` — one extra trailing newline (expected 183).
  Its screenshot-after-every-step verification never caught it: a trailing
  blank line is invisible on screen, and the driver's own RESULT line claimed
  "all 10 lines and a final newline". Observation count proxy: 207 screenshot
  mentions in its log.
- **Run B** entered the document as one batched text action, which made the
  content byte-exact by construction (183 bytes, hash matches). It verified by
  state (window titles, editor saved state, folder listing) with only 19
  screenshot mentions in its log, and its RESULT claim matches ground truth.
  Both apps closed, root copy absent.
- **Where lean hurt:** B burned a few early calls on cua CLI syntax errors
  (missing `combo`/`text` arguments, one `--help` probe) before settling into
  the run. Those wasted calls are inside its 52,372 tokens; putting the exact
  CLI signatures in the prompt would widen the gap further.
- **Where lean did not help much:** action count barely moved (34 vs 37). The
  Files folder-create + move sequence is many small GUI steps in both
  profiles; the savings came from observation cost (crops/OCR/text instead of
  full screenshots) and a shorter carried context, not from fewer clicks.

## Honest caveats

- One run per profile, one small task. Codex `tokens used` totals include
  context reprocessing and vary between runs; treat the percentages as
  directional, not constants.
- The accuracy inversion is real but task-shaped: this bench's only defect
  class (byte-level text difference) is exactly the one screenshots cannot
  see and a single exact text entry cannot make. On a visually ambiguous
  task, text-first observation carries the opposite risk; it did not bite here.
- Methodology note: the pre-run desktop-busy checks initially self-matched
  (the `pgrep -f "codex exec"` pattern matched the checker's own command
  line) and reported the desktop busy for ~25 minutes while it was free.
  Diagnosed with `ps`, fixed with a bracket pattern; both runs then launched
  on a verified-free desktop, one driver at a time (confirmed by `ps`
  during run B). No effect on the runs themselves.
