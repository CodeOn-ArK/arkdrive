# WM Spike A — Xvfb dual-session isolation qualification

- Plan: ArkDrive Agentic WM, Phase 0 probe (1) — private Xvfb plus private accessibility bus.
- Date: Nov 9, 2026 (evening PT). Host: ArK2 (arktx), run entirely headless; the real desktop session, mouse, and Chromium were never touched.
- Harness: `~/wm-spike-a/spike.sh` + `probe.py` (pyatspi) on ArK2; run logs and per-run archives (`run1/`, `run2/`) alongside. Final results below are run 3.
- Setup per session: own Xvfb (S1 `:91`, S2 `:92`, chosen to avoid the pre-existing portal-lane displays `:11`–`:15`), own `dbus-daemon --session` (private address + PID), own AT-SPI launcher + registry, own `HOME` and `XDG_RUNTIME_DIR` under `~/wm-spike-a/`.
- Apps: session 1 = GNOME Calculator, session 2 = Thunar (distinct names make cross-talk checks unambiguous).
- Prerequisite: `xvfb` was not installed on ArK2; installed via `sudo apt-get install -y xvfb` (2:21.1.22-1ubuntu1.3).

## Observations (not failures of the spike goal)

1. **AT_SPI_BUS root property not set in dual-session runs.** In runs 2–3, `xprop -root AT_SPI_BUS` on `:91`/`:92` returned "not found" even while pyatspi was connected and reading the correct per-session trees; address discovery fell back to the session-bus `GetAddress` path. In single-session diagnostics (`diag.sh` on `:93`, `diag2.sh` on `:94`, kept on the box) the same xprop query DID return the address, matching gdbus exactly. Something about the two-session case changes who publishes the property; root cause not identified. Worth carrying into Phase 0's "reproduce the accessibility outage without assuming its root cause" item: any ArkDrive discovery code must use `GetAddress`, not rely on the X property alone.
2. **Thunar's AT-SPI application name is lowercase `thunar`** (GNOME Calculator's is `gnome-calculator`). Name-matching code must be case-aware per app.
3. The gdbus address strings in `results.txt` carry a trailing `',)` — a parsing artifact of gdbus's tuple output format, not part of the address.

## Runs 1–2 (harness defects, fixed before run 3; archived on the box)

- Run 1 FAILs were measurement defects in the harness, not isolation failures: AT-SPI address probed via the X root property before any client had activated the bus (both empty), and Thunar matched as `Thunar` instead of `thunar`. Verbatim: `CHECK session1_atspi_bus_up FAIL addr=`, `CHECK atspi_buses_distinct FAIL s1='' s2=''`, `CHECK session2_app_a11y_visible FAIL app=Thunar time_to_visible_s=29.29` (the 29.29s is the full poll timeout; the same run's tree dump shows `a11y S2: xdg-desktop-portal-gtk,thunar`). All isolation/absence checks already passed in run 1.
- Run 2 fixed the name case and moved address capture after app launch; app checks passed (0.66s each) but the xprop property was still unset (see observation 1), so the AT-SPI address checks still failed on method.
- Run 3 switched address capture to `org.a11y.Bus.GetAddress`: all 15 checks PASS, wall 4s (warm caches; runs 1–2 took 55s/26s including full poll timeouts).
